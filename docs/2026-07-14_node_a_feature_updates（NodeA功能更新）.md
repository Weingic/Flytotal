## 开发板重启可诊断与单段证据防拼接

真实运行中出现一次 `timestamp_ms` 从约 513 秒回到约 71 秒，证明开发板发生过重启。旧固件没有保存复位原因，现场只能看到融合、云测试状态恢复默认值，无法区分拔插、下载复位、看门狗、崩溃或电压异常；旧记录器也没有启动编号，理论上可能把一次试验中的重启前后采样合并。

固件现为每次启动生成唯一 `boot_id`，并输出 RTC 保留启动计数、ESP 高层复位原因、ESP32-S3 原始复位码和运行时长。串口桥保存这些字段，并在同一桥进程看到新启动编号时增加 `node_boot_change_count`。ESP-IDF 对本机 USB 下载复位返回高层 `UNKNOWN`，底层原始码为 `21`；固件已将其准确解释为 `USB_UART`，避免把正常烧录复位误报成未知故障。

出发预检的 `node_online_fresh` 现在同时要求启动编号和有效复位原因存在，并要求当前启动及桥接观察均稳定至少 15 秒。单次试验记录器逐样本保存启动编号、复位原因和运行时长；一段内出现多个启动编号或运行时长倒退时，`node_boot_session_valid=false`、`node_reset_observed=true`，整段固定为 `INVALID_TRIAL`。矩阵总门也拒绝缺少该证明的旧报告。

该改动不改变 `TrackManager -> HunterAction -> GimbalController -> UPLINK` 主链，不开启舵机。回归先因缺少 `node_boot_session_valid` 红灯，再完成稳定启动正例、双启动编号反例、预检缺字段/刚重启反例和串口解析反例；完整回归为 `25/25 PASS`，最终物理同场夹具仍为 `GO 26/26`。
